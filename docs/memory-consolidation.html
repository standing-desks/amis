03 · Review

Approve the meaning, then the destination changes.

You can keep the original notes, edit the proposal, accept it or reject it. Accepting it into the library is separate from sharing it with an agent.

1
Review the claim and its evidence.

See both source notes beside the proposal. Confirm that the wording and Atlas-only scope are right.

2
Choose the destinations and inspect the exact changes.

See the files or resources that would change, what would be preserved, and anything the destination cannot represent.

3
Approve that plan.

A changed destination, permission, source decision or scope requires a fresh check. The original approval cannot authorize different changes.

Your app owns permission. A memory's text, a model response or an imported “approved” label cannot grant write access.

05 · Check

Show what the app can actually verify.

A saved file is the first step. The app keeps delivery evidence per destination and makes gaps visible.

Discoverable

Observed in a particular agent context. Until that is checked, loading remains unverified.

Evidence has a context and a lifetime. Changes to the file, configuration or agent version require a fresh check. Loading does not guarantee future recall or compliance.

06 · Undo

Reverse owned changes while protecting newer work.

Imagine both destinations later received the memory, then you manually edited one copy. Undo needs to account for that newer edit.

  1. Stop this memory from being republished.Cancel waiting changes and hold work derived from the undone memory for review.
  2. Prepare corrections for the app's own changes.Keep the original source notes and history. Show which destinations can be corrected safely.
  3. Preserve your manual edit.A changed destination is a conflict to resolve. Undo does not restore an old whole-file snapshot over it.

Undo has honest limits. The app shows when recovery data has expired. Already-running contexts or external copies may still contain the old memory.

Step 1 of 6 · Collect

You stay in control

Three choices to make at setup.

01 / SOURCES & SCOPE

What may be collected?

Choose allowed sources and confirm project boundaries. Global preferences and project knowledge keep their separate scope.

02 / CONSOLIDATION

How are proposals prepared?

Choose deterministic rules or a local or hosted model. A hosted model receives the selected memory content; that choice is explicit.

03 / PUBLICATION

What can happen automatically?

The initial flow uses explicit approval for native changes. Later, a narrowly configured local policy could approve routine changes, with recorded decisions and exception review.

When things change

The important edge cases.

Two agents remember different answers.

Keep both claims and their evidence. Ask for a resolution or narrower scopes. Timestamp order and repeated wording do not establish which answer is correct.

An original memory is withdrawn.

Hold dependent proposals and publication, even if the combined memory has a new identity. Track corrections for copies already published. Unrelated knowledge remains available.

The app closes halfway through a change.

On reopening, reconcile each saved step with the actual destination. Preserve successful work, resume valid pending work, and surface conflicts. An interrupted operation is never assumed to have rolled back.

An agent reads back a shared copy.

An unchanged copy with the app's own delivery record creates no new memory or extra evidence. A native edit becomes something to reconcile against the original publication.

AMIS defines the contract.

Identity, scope, history, evidence, compatibility and delivery rules. The repository holds the spec, schemas, examples and documentation.

Each app owns its implementation.

Twine and other consumers own their memory library, converters, validators, approvals, background work, recovery and native integration tests.

What TWINE-77 is doing now: specifying the rules behind this experience, including feature requirements, derived-memory withdrawal, shared-resource coordination and delivery evidence. The technical proposal is a draft alongside the current 0.4.0 contract.
